# Product research: Android work-time trackers

**Дата исследования:** 2026-09-08  
**Главный референс:** «Табель учета рабочего времени» — RavenDEV (`com.dev.workshiftcalendar`)

## 1. Цель исследования

Не копировать существующий продукт, а понять:

- какие задачи пользователи уже считают обязательными;
- за что ценят календарный формат;
- где существующие приложения становятся медленными и перегруженными;
- какие функции должны быть на первом плане, а какие — по запросу;
- какие проблемы нельзя переносить в новый продукт.

## 2. Главный референс — «Табель учета рабочего времени»

Google Play: <https://play.google.com/store/apps/details?id=com.dev.workshiftcalendar&hl=ru>

На момент исследования приложение имеет более 1 млн установок и десятки тысяч отзывов. Его базовая модель доказала жизнеспособность: пользователь открывает календарь, выбирает день и сохраняет рабочие данные прямо относительно даты.

### 2.1. Что в референсе работает хорошо

Сохраняем как продуктовые идеи:

- **календарь — главная поверхность**, а не отдельный вторичный отчёт;
- запись привязана к конкретной дате и доступна в один-два действия;
- учёт рабочих часов;
- учёт переработки;
- ставка/заработок;
- заметка к дню;
- месячная агрегация;
- экспорт/отчётность как естественное продолжение накопленных данных.

Это правильная ментальная модель для человека, который хочет ответить на три вопроса: «сколько я работал», «сколько заработал» и «что было в конкретный день».

### 2.2. Что устарело или ухудшает UX

По текущему интерфейсу и пользовательским отзывам:

1. **Слишком высокая информационная плотность календаря.** В маленькой ячейке одновременно находится несколько значений, используются тонкие границы, цветовые кодировки и мелкая типографика. Быстрое считывание месяца становится сложнее.
2. **Слишком много элементов управления рядом с календарём.** Управление периодом и расчётами конкурирует с основной задачей — выбрать день.
3. **Слабая визуальная иерархия.** Даты, часы, суммы и служебные элементы имеют близкий визуальный вес.
4. **Редактирование воспринимается как форма, а не быстрое действие.** Для частой ежедневной операции это слишком тяжёлый паттерн.
5. **Полноэкранная реклама ломает серийный ввод.** В отзывах 2026 года повторяется жалоба на рекламу после практически каждого сохранения/действия. Особенно плохо это работает, когда пользователь заполняет несколько прошедших дней подряд.
6. **Внешний вид не соответствует современному Android interaction model:** нет ощущения edge-to-edge, современной композиции Material 3, адаптивных размеров и цельной motion-системы.

### 2.3. Что не нужно копировать

- плотную «таблицу Excel» на телефоне;
- несколько чисел в каждой ячейке календаря;
- постоянные стрелки/переключатели для действий, которые удобнее решить свайпом или contextual action;
- отдельный цвет для каждого типа данных без второго семантического признака;
- длинную форму редактирования дня;
- агрессивные interstitial ads;
- устаревшие форматы отчётов как единственный путь экспорта.

## 3. Аналоги

### 3.1. Timesheet: Рабочий график смен

Google Play: <https://play.google.com/store/apps/details?id=com.konstantin.timetracker>

Сильные стороны:

- календарная модель;
- шаблоны смен;
- автоматический расчёт заработка;
- хорошее соответствие локальному сценарию сменной работы.

Полезные сигналы из отзывов 2026 года:

- пользователи негативно воспринимают редко используемый блок автозаполнения на главном экране;
- длинное редактирование дня заставляет прокручивать экран ради базового действия;
- востребованы свайпы между месяцами;
- стрелки в верхней части экрана неудобны на больших телефонах;
- востребованы несколько графиков/профилей и отпускные сценарии.

**Вывод:** progressive disclosure обязателен. Свайп месяца должен быть основным быстрым жестом, а не единственным способом через маленькие верхние кнопки.

### 3.2. WorkingHours — Time Tracking

Google Play: <https://play.google.com/store/apps/details?id=partl.workinghours>

Сильные стороны:

- простое начало/остановка учёта времени;
- проекты, теги и задачи;
- ручная корректировка;
- экспорт;
- кроссплатформенность.

Отзывы часто хвалят именно сочетание функциональности и понятного UI.

**Вывод:** сложная модель данных допустима, если первичный путь остаётся коротким. Проекты/теги не должны быть обязательными для обычной записи рабочего дня.

### 3.3. Simple Time Tracker

Google Play: <https://play.google.com/store/apps/details?id=com.razeeman.util.simpletimetracker>

Сильные стороны:

- offline-first;
- без рекламы и обязательного аккаунта;
- открытый исходный код;
- быстрые действия;
- backup/restore;
- widgets и dark theme.

**Вывод:** доверие и локальность данных — самостоятельное продуктовое преимущество. Для персонального табеля сеть не нужна в core flow.

### 3.4. Time Recording — Timesheet App

Google Play: <https://play.google.com/store/apps/details?id=com.dynamicg.timerecording>

Сильные стороны:

- очень зрелый набор функций;
- check-in/check-out;
- задачи и заметки;
- отчёты PDF/Excel/HTML;
- интеграции, backup/sync, widgets, Wear OS, NFC.

Слабая сторона как референса для нового UI — большое количество возможностей неизбежно повышает сложность навигации и настроек.

**Вывод:** это хороший reference catalogue для будущих возможностей, но плохой аргумент переносить всё в MVP.

### 3.5. Timesheet — Work Hours Tracker

Google Play: <https://play.google.com/store/apps/details?id=com.aadhk.time>

Сильные стороны:

- часы, зарплата, overtime;
- несколько клиентов/проектов;
- отчёты и invoices.

Повторяющиеся жалобы относятся к рекламе/цене разблокировки и сложности части меню.

**Вывод:** монетизация не должна мешать самой частой операции — записи рабочего времени.

## 4. Общие продуктовые паттерны рынка

### Пользователи ожидают в core

- календарь или очень быстрый доступ к истории по датам;
- ручное добавление/редактирование;
- часы/минуты;
- заработок;
- переработка;
- заметки;
- месячные итоги;
- понятный экспорт.

### Пользователи часто хотят после core

- несколько мест работы/профилей;
- сменные шаблоны (`2/2`, `3/3`, и т. п.);
- отпуск, больничный, выходной;
- start/end + breaks вместо только итогового количества часов;
- виджеты и быстрые действия;
- PDF/XLSX/CSV;
- backup/sync;
- годовые отчёты;
- напоминания;
- timer/check-in/check-out.

Эти возможности важны, но не должны одновременно появляться в первом интерфейсе.

## 5. Ключевые продуктовые решения WorkTime

### 5.1. Calendar-first, но не spreadsheet-first

Календарь остаётся центральным элементом. В ячейке показываем только:

- число месяца;
- одно короткое рабочее значение (`8 ч`, `7:30` или эквивалент выбранного формата);
- минимальный семантический индикатор особого состояния, если оно действительно нужно.

Заработок, overtime, note и детали не пытаемся упаковать в ту же ячейку.

### 5.2. Быстрое редактирование через bottom sheet

Тап по дню открывает короткую модальную панель. Первый слой содержит только частые поля. Редкие настройки раскрываются через «Дополнительно».

Цель: нормальная запись дня должна выполняться без перехода на отдельный экран и без вертикального скролла на типичном телефоне.

### 5.3. Сводка вместо россыпи цифр

Над/под календарём отображается компактная месячная сводка:

- отработано;
- заработано;
- переработка.

Подробная статистика — отдельная secondary surface.

### 5.4. Offline-first

Core не требует:

- аккаунта;
- сети;
- облачного backend;
- рекламного SDK;
- аналитического SDK.

Все записи хранятся локально. Export/backup может использовать системный Storage Access Framework/share sheet без широкого storage permission.

### 5.5. Сначала один рабочий профиль

Несколько работ — реальный запрос рынка, но сначала нужна безошибочная single-profile модель. Схема данных должна позволять расширение без переписывания всего приложения.

### 5.6. Не угадывать правила оплаты переработки

Overtime — предмет трудового договора/юрисдикции. В первой версии:

- `worked time` — фактически оплачиваемое рабочее время;
- `overtime` — отдельная часть/метка для сводки;
- базовый заработок считается по полной длительности и базовой ставке;
- повышающий коэффициент не применяется скрыто.

Настраиваемые overtime rules можно добавить позже как явную функцию.

## 6. Продуктовые риски

| Риск | Защита |
|---|---|
| Календарь снова станет перегруженным | жёсткий content budget для day cell |
| Bottom sheet превратится в длинную форму | частые поля сверху, advanced collapsed |
| Расчёты денег дадут ошибки | integer minor currency units + unit tests |
| Расширение до нескольких работ сломает storage | repository boundary и versioned Room migrations |
| Слишком ранняя архитектурная сложность | single app module + manual DI в первой версии |
| «Современный» UI станет декоративным | motion только для state/spatial continuity, accessibility first |
| Реклама разрушит UX | interstitial ads запрещены в core entry flow |
