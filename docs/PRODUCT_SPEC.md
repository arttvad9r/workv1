# WorkTime — Product specification

**Версия:** 0.1  
**Дата:** 2026-09-08

## 1. Product statement

WorkTime — персональный Android-табель, в котором пользователь видит месяц целиком, быстро заносит фактически отработанное время и получает достоверную сводку по часам, заработку и переработке.

Главная цель продукта — минимизировать стоимость регулярного действия. Добавление обычного рабочего дня не должно ощущаться как заполнение бухгалтерской формы.

## 2. Основной пользовательский сценарий

```text
Открыть приложение
→ увидеть текущий месяц и его сводку
→ выбрать день
→ указать отработанное время
→ сохранить
→ сразу увидеть обновлённый календарь и итог месяца
```

Для типичного рабочего дня этот flow должен занимать несколько секунд и не требовать отдельного полноэкранного editor screen.

## 3. MVP scope

### P0 — обязательно для первого рабочего релиза

1. Календарь месяца.
2. Переход между месяцами свайпом.
3. Быстрый выбор конкретного дня.
4. Создание/редактирование записи дня.
5. Поля:
   - отработанное время;
   - переработка;
   - необязательная заметка.
6. Настройка базовой почасовой ставки.
7. Необязательная ставка-override для конкретного дня — после базового вертикального среза, если не ухудшает форму.
8. Месячная сводка:
   - суммарно отработано;
   - суммарно overtime;
   - заработок.
9. Локальное offline storage.
10. Удаление записи дня с понятным подтверждением/undo-паттерном.
11. Светлая и тёмная тема либо корректное следование системной теме; конкретный вариант фиксируется на этапе design-system implementation.
12. Accessibility базовых flows.
13. Adaptive layout для compact и expanded window.

### P1 — следующий продуктовый слой

- day types: работа / выходной / отпуск / больничный;
- start/end time + breaks как альтернативный способ ввода;
- пресеты типичных смен;
- автозаполнение графика (`2/2`, `3/3`, custom pattern);
- подробная статистика;
- CSV/XLSX/PDF export;
- backup/restore;
- calendar search/filter;
- годовая сводка;
- widget / quick action;
- reminders.

### P2 — только после стабилизации core

- несколько мест работы/профилей;
- sync между устройствами;
- опциональный аккаунт;
- совместный/работодательский режим;
- Wear OS;
- timer/check-in/check-out;
- сложные overtime/rate rules;
- invoices.

## 4. Что сознательно НЕ входит в MVP

- сервер;
- регистрация;
- обязательная сеть;
- рекламный SDK;
- аналитический SDK;
- location/geofencing;
- контактные/календарные permissions;
- фоновые foreground services;
- автоматическое распознавание смен;
- сложная payroll/налоговая логика;
- проекты/клиенты/теги как обязательные сущности.

## 5. Модель времени

### 5.1. Единица хранения

Рабочая длительность хранится в **целых минутах**.

Причины:

- избегаем floating-point ошибок;
- удобно суммировать;
- легко форматировать как `8 ч`, `7 ч 30 мин`, `7:30`;
- достаточно точно для персонального табеля.

### 5.2. Отработанное время

`workedMinutes` — вся оплачиваемая длительность дня.

### 5.3. Переработка

`overtimeMinutes` — часть/показатель времени, которую пользователь считает переработкой.

Ограничение:

```text
0 <= overtimeMinutes <= workedMinutes
```

Если в будущем появятся режимы, где overtime учитывается вне `workedMinutes`, это должно быть отдельной явно мигрированной моделью, а не скрытым изменением смысла поля.

## 6. Модель денег

Деньги хранятся в **minor units** (`Long`): копейки/центы и т. п., а не `Double`.

### MVP calculation

```text
earnings = round(workedMinutes × hourlyRateMinor / 60)
```

Округление должно иметь одну документированную стратегию и unit tests на граничные значения.

### Overtime pay

MVP не предполагает коэффициент `1.5x`, `2x` или любой другой автоматически. Это нельзя безопасно угадать: правила отличаются по трудовому договору, стране и работодателю.

## 7. Модель даты

Обычная дневная запись привязана к **локальной календарной дате**, а не UTC instant.

Для MVP достаточно ISO `YYYY-MM-DD` в persistence layer либо Room type converter вокруг `LocalDate`.

Это предотвращает ошибку, когда запись «8 часов за 8 сентября» внезапно становится записью за 7/9 сентября после смены timezone.

## 8. Настройки

Минимальный набор:

- базовая почасовая ставка;
- код/символ валюты;
- тема: system/light/dark, если пользовательский переключатель реализован;
- формат длительности, если будет доказана потребность.

Редкие настройки не должны находиться на календарной поверхности.

## 9. Empty / first-run experience

Первый запуск не должен начинаться с многошагового onboarding.

Базовый вариант:

1. сразу показать текущий месяц;
2. в сводке — нули;
3. лёгкая contextual подсказка: «Нажмите на день, чтобы добавить часы»;
4. ставка может быть запрошена при первом сохранении/попытке увидеть заработок либо через settings; отсутствие ставки не блокирует учёт часов.

## 10. Day edit flow

### Базовое состояние

Bottom sheet:

- дата;
- `Отработано`;
- `Переработка`;
- `Заметка` как компактное поле/раскрываемая секция;
- `Сохранить`.

### Правила

- сохранение disabled при некорректных данных;
- ошибка объясняется рядом с полем;
- raw exceptions не показываются;
- повторный тап по заполненному дню открывает существующие значения;
- удаление не конкурирует визуально с primary action;
- клавиатура не должна закрывать активное поле или кнопку сохранения.

## 11. Month navigation

Primary interaction:

- горизонтальный swipe по календарю.

Secondary/accessibility alternatives:

- явные previous/next month actions с touch target не меньше 48 dp;
- переход к текущему месяцу, если пользователь ушёл далеко.

Back не должен использоваться как «вернуться к текущему месяцу»; системный Back сохраняет платформенную семантику.

## 12. Month summary

Показывает только три наиболее полезных значения:

- часы;
- заработок;
- overtime.

Детальные breakdowns не должны разрастаться в dashboard на главном экране.

## 13. Delete semantics

Удаление дневной записи — обратимое/осознанное действие.

Предпочтительный UX:

- удалить из day sheet;
- закрыть sheet;
- Snackbar `Запись удалена` + `Отменить`.

Если undo технически ещё не реализован, требуется подтверждение до удаления.

## 14. Export semantics (P1)

Экспорт обязан быть предсказуемым:

- период явно указан;
- единицы и валюта указаны;
- формат данных документирован;
- экспорт не меняет локальные записи;
- используется system document picker/share sheet;
- приложение не просит broad storage permission.

Приоритет форматов:

1. CSV — простой interoperable data export;
2. XLSX — удобен для бухгалтерии/таблиц;
3. PDF — удобен как фиксированный отчёт.

## 15. Privacy promise

Для MVP:

- данные остаются на устройстве;
- приложение не требует аккаунта;
- приложение не отправляет записи рабочего времени на backend;
- нет advertising ID;
- нет скрытой аналитики.

Если это когда-либо изменится, privacy model и Data Safety должны быть пересмотрены до добавления SDK/сети.

## 16. Product acceptance criteria для core

Core считается рабочим, когда пользователь может:

1. установить приложение;
2. открыть его без сети;
3. добавить запись за сегодня;
4. добавить запись за другой день текущего месяца;
5. изменить запись;
6. закрыть приложение;
7. перезапустить/пересоздать процесс;
8. увидеть сохранённые данные;
9. перейти в соседний месяц;
10. вернуться и получить те же суммы;
11. увеличить font scale без потери critical actions;
12. использовать system Back/predictive Back без неожиданного reset state.

## 17. Product success metrics без analytics SDK

До появления осознанной телеметрии качество оценивается через:

- время/число действий для добавления обычного дня;
- количество UI элементов на primary screen;
- ручные usability-прогоны;
- тестовые сценарии;
- crash/ANR после публикации через Play Vitals;
- пользовательскую обратную связь.

Цель MVP — не максимальный feature count, а минимальное friction в ежедневном учёте.
